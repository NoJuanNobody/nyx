# Ticket #239 — Repo selector for ticket creation flows

## What was implemented

A repository selector dropdown was added to both ticket creation flows so users can explicitly choose which GitHub repository issues are sent to.

### Frontend changes

**`apps/web/src/components/CreateTicketModal.tsx`**
- Added `RepoOption` interface (`owner`, `name`, `fullName`)
- Derives available repos from the GitHub integration's `selectedRepos` config field
- Renders a `<select data-testid="repo-selector">` when GitHub is selected and multiple repos are configured
- Defaults to `selectedRepos[0]` on modal open; resets to null when modal closes
- Passes `repo: { owner, name }` to `createTicket()` when provider is GitHub

**`apps/web/src/components/BulkTicketReview.tsx`**
- Same `RepoOption` interface and derivation logic
- Added a `fetchIntegrations` query (using the `teamId` prop, which was previously unused/discarded)
- Renders a `<select data-testid="bulk-repo-selector">` in the modal header, to the left of the provider toggle
- Passes `repo` to `bulkApproveSuggestions()`

**`apps/web/src/lib/api.ts`**
- `createTicket()` — added optional `repo?: { owner, name }` field to the data param
- `bulkApproveSuggestions()` — added optional `repo?: { owner, name }` third argument, forwarded in request body

### Backend changes

**`apps/api/src/routes/tickets.ts`**
- `POST /api/documents/:documentId/tickets` — destructures optional `repo` from request body and passes to `ticketService.createFromDocument()`

**`apps/api/src/routes/suggestions.ts`**
- `POST /api/ticket-suggestions/:id/approve` — passes optional `repo` through to `suggestionService.approve()`
- `POST /api/ticket-suggestions/bulk-approve` — passes optional `repo` through to `suggestionService.bulkApprove()`

**`apps/api/src/services/ticket.service.ts`**
- `createFromDocument()` — accepts optional `repo?: { owner, name }` as 6th argument
- Priority order for GitHub owner/repo: `repo` param → `selectedRepos[0]` → legacy `owner`/`repo` config fields
- All existing fallback behaviour is preserved; no breaking changes

**`apps/api/src/services/suggestion.service.ts`**
- `approve()` — accepts and forwards `repo?` to `ticketService.createFromDocument()`
- `bulkApprove()` — accepts and forwards `repo?` to `ticketService.createFromDocument()` for each suggestion in the loop

### Tests updated

- `apps/api/src/__tests__/routes/tickets.test.ts` — added test that verifies `repo` is passed through to the service
- `apps/api/src/__tests__/routes/suggestions.test.ts` — added tests for `approve` and `bulk-approve` repo forwarding; also fixed mock to include all service methods (was missing `bulkApprove` etc.)
- `apps/api/src/__tests__/services/ticket.service.test.ts` — added test that an explicit `repo` param overrides `selectedRepos[0]`
- `apps/api/src/__tests__/services/suggestion.service.test.ts` — added test that `approve()` forwards the `repo` param correctly; updated existing assertion to include the new `undefined` 6th argument

**All 990 tests pass.**

## Acceptance criteria status

- [x] Users can choose which repository tickets are created in
- [x] Repo selector appears in ticket creation flows (manual `CreateTicketModal` and bulk `BulkTicketReview`)
- [x] Selected repo is passed to the ticket creation API

## Notes

- The selector is only shown for GitHub (Jira uses project key, not a repo concept)
- When only one repo is configured the dropdown still appears so users have visibility over where issues go
- Jira flow is unaffected; the `repo` param is ignored for Jira payloads
