# Ticket #340 -- Template picker modal trapped inside sidebar

## Root cause

`TemplatePicker` used `fixed inset-0` expecting the viewport, but it was
rendered as a DOM descendant of `<Sidebar />` (via `<FileTree />`). The Sidebar
applies `md:translate-x-0` to support a mobile slide-in animation. Any non-none
`transform` on an ancestor creates a containing block for `position: fixed`
descendants, so the modal's `inset-0` resolved to the Sidebar's ~250px-wide
bounding box instead of the viewport. Every downstream symptom (left-docked
strip, 8-character truncated template names, clipped stage filter pills,
cramped tab row) followed from that.

## Changes

1. **`apps/web/src/components/Portal.tsx`** (new, 38 lines) -- Tiny shared
   `<Portal />` wrapper around `createPortal(children, document.body)` from
   `react-dom`. Mounts on client only (guarded via a `mounted` state so SSR /
   first paint doesn't hit `document`). Accepts an optional `container` prop
   for tests. Intended for reuse by any future overlay that needs to escape
   ancestor `transform` containing blocks.

2. **`apps/web/src/components/TemplatePicker.tsx`** -- Wrapped the modal's
   return tree in `<Portal>...</Portal>`. Added `data-testid` attributes on
   the backdrop and card nodes so the Playwright regression test can target
   them deterministically. No other logic, styling, or structure changed --
   the `fixed inset-0 z-50 flex ... bg-black/40` backdrop, the
   `max-w-2xl rounded-xl bg-white shadow-2xl` card, `onClick={onClose}`
   backdrop handler, and the `e.stopPropagation()` inside-card handler are
   preserved. The backdrop/card are now DOM children of `document.body`,
   outside the Sidebar's transform containing block, so `inset-0` resolves to
   the viewport.

3. **`apps/web/src/components/Sidebar.tsx`** -- **Not modified.** Per the
   ticket's explicit instructions, `md:translate-x-0` was kept to preserve
   the mobile slide-in/slide-out animation. The portal is the correct fix.

4. **`e2e/template-picker.spec.ts`** (new) -- Playwright regression test at
   a 1280x800 viewport that:
   - Opens the picker via the Explorer header "New from template" button
   - Asserts backdrop and card are NOT descendants of `<aside>`
     (portal sanity check)
   - Asserts backdrop bounding rect is exactly 1280x800 at (0, 0)
     -- full viewport
   - Asserts card width is 672px +/- 4px (max-w-2xl)
   - Asserts card is horizontally centered within +/- 2px
   - Asserts full seeded template names render
     ("Product Requirements Document (PRD)", "Problem Statement")
     -- no 8-character truncation
   - Verifies click-inside-card does not close (stopPropagation)
   - Verifies backdrop click closes the modal

5. **`e2e/fixtures/test-base.ts`** -- Added a `SEEDED_TEMPLATES` constant
   with a handful of canonical built-in templates (Problem Statement,
   Value Proposition Canvas, PRD, ADR) matching the real names in
   `apps/api/src/db/seed-templates.ts`, and registered a
   `page.route('**/api/templates**', ...)` mock in `setupApiMocks` that
   returns them for GET requests. This lets the new test assert on full
   template names without depending on live DB state and also keeps the
   picker populated for any future tests that open it.

If they are only ever rendered from top-level routes / `<Layout />` (not under
the Sidebar), they are fine as-is. A follow-up audit should confirm and
portal them proactively.
