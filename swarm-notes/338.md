# swarm-notes/338.md — Preserve scroll position across editor views and sync split panes

## Summary
Two coupled scroll-UX bugs in `apps/web/src/pages/DocumentEditor.tsx`:

1. Toggling between Markdown / Split / Preview unmounted whichever pane
   was absent, so each view switch reset the relevant scroll container
   to `scrollTop = 0`. Users lost their place after every click.
2. In Split view, the editor textarea and the preview wrapper scrolled
   completely independently. The line being edited and its rendered
   counterpart drifted out of alignment immediately, defeating the
   point of split view.

## Fix — Bug 1 (scroll preservation)
- Stopped unmounting the editor and preview panes. Both `<div>`s are
  now rendered unconditionally and toggled with inline
  `display: 'none' | 'flex'` based on `editorLayout`. Native scroll
  state is preserved by the browser across visibility toggles, so no
  ref-juggling is needed and there is no `scrollTop = 0` flash on
  hydration. Width is still driven by `splitPercent` in inline `width`,
  matching the prior layout exactly.
- The split drag handle continues to render only when
  `editorLayout === 'split'` (it is purely additive UI, not a scroll
  surface, and rendering it in non-split modes would be wrong).
- The MarkdownEditor's textarea is the same `<textarea>` instance
  across view switches, so its `scrollTop` is naturally retained.
- The preview wrapper now exposes a `previewScrollRef` so the new
  scroll-sync effect can attach a listener directly to the element
  that owns `overflow-y-auto`.
- Scroll state is in-memory only — nothing is persisted to
  `localStorage`. Closing the doc or opening a different doc resets
  scroll naturally because the `DocumentEditor` instance unmounts.

## Fix — Bug 2 (split scroll sync)
- Added a `useEffect` keyed on `[editorLayout]` that only attaches
  scroll listeners when the layout is `'split'`. It cleans up on
  layout change so the listeners do not run in `'editor'` or
  `'preview'` modes.
- Bidirectional ratio sync: when one pane fires a `scroll` event, the
  effect computes `ratio = scrollTop / (scrollHeight - clientHeight)`
  on the source and writes
  `target.scrollTop = ratio * (targetMax)` on the other pane, wrapped
  in `requestAnimationFrame` to avoid layout thrash.
- **Leader-lock** via `scrollLeaderRef` (a `useRef<HTMLElement | null>`)
  prevents infinite ping-pong: when the user scrolls pane A, A claims
  the leader for ~120ms; programmatic scrolls on the follower
  short-circuit because `scrollLeaderRef.current !== ownEl`. The
  120ms timeout is the portable replacement for the (Safari-missing)
  `scrollend` event.
- A no-op-write guard skips updates when the follower is already
  within 0.5px of the target, which avoids the rare case where rounding
  produces a phantom scroll event after the lock has expired.
- Scroll sync is suspended while the user is dragging the split
  resize handle. `handleSplitDragStart` now sets
  `isDraggingSplitRef.current = true` on pointerdown and clears it on
  pointerup, and both scroll handlers bail out while the flag is set.
  This stops the pane width animation from yanking the other pane's
  scroll.
- Sync re-attaches automatically when the user toggles back into
  Split (the `[editorLayout]` effect re-runs), and both panes resume
  from their preserved scroll positions because of the Bug 1 fix.

## Tests added
**`e2e/editor-scroll.spec.ts`** — three Playwright regression tests:

1. **Scroll preservation across view switches.** Loads a long doc
   (400 paragraphs) via a route override, scrolls the textarea to
   ~50% in Markdown view, hops Markdown → Preview → Split → Markdown,
   asserts the textarea's `scrollTop` is within 24px (≈ 1 line) of
   the original.
2. **Split sync — editor leads.** In split view, scrolls the editor
   to 50% of its scrollable range, waits one rAF tick, asserts the
   preview pane's fractional position
   (`scrollTop / (scrollHeight - clientHeight)`) matches the editor's
   within ε = 0.02.
3. **Split sync — preview leads (reverse direction).** Same shape as
   #2 but scrolls the preview to 40% and asserts the editor follows.

The tests install a per-test `page.route` override on
`GET /api/documents/:id` that returns a long-form markdown body so
the scroll containers actually have somewhere to scroll. The override
falls back to the default mock for non-GET methods.
