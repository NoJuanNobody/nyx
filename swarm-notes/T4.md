# T4: Hook Notifications Into Domain Events

## What was done

### 1. Created notification events constants
- **File:** `apps/api/src/services/notification-events.ts`
- Defines `NotificationEvents` const object with event type strings: `drift.detected`, `ticket.created`, `ticket.updated`, `team.invite`, `document.shared`

### 2. Ticket creation notification
- **File:** `apps/api/src/routes/tickets.ts`
- After a ticket is created via `POST /api/documents/:documentId/tickets`, we fetch the document owner (`createdById`) and `teamId`, then fire a notification with `eventType: 'ticket.created'`
- Notification is sent to the **document owner**, not the ticket creator (who already knows)
- Wrapped in `.catch(() => {})` so it never blocks the primary response

### 3. Team invite / member added notification
- **File:** `apps/api/src/routes/teams.ts`
- When an existing user is added directly to a team via `POST /api/teams/:id/members`, we notify that user with `eventType: 'team.invite'`
- For **pending invitations** (user doesn't have an account yet), no in-app notification is created since there is no `userId` to target. The email invite already covers this case.

### 4. Document shared
- **Skipped.** No document sharing endpoint exists in the codebase. This hook can be added when that feature is built.

## Build & test results
- `pnpm build` passes (all 4 packages)
- `pnpm --filter api test` passes (63 test files, 413 tests)

## Notes
- All `notificationService.create()` calls use `.catch(() => {})` to ensure notifications never block primary actions
- The notification service already handles deduplication (10-minute window by `entityId`) and user preference checks
