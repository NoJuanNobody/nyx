# Ticket 347 — Make the purple accent color consistent across light and dark mode

## Root cause

`apps/web/src/index.css` already used a CSS-variable-swap strategy to
remap `--color-blue-50` through `--color-blue-950` to a purple/violet
hue (~287°) so that every Tailwind `bg-blue-*`, `text-blue-*`,
`border-blue-*`, `ring-blue-*`, `outline-blue-*`, etc. utility renders
as the brand purple — without touching component files. But that
remap lived only inside the `.dark { ... }` selector (lines 38-51).

In light mode there was nothing remapping the blue variables, so every
component using a `blue-*` utility (under the assumption that the swap
applies in both modes) rendered as actual Tailwind blue. The brand
accent was visually purple in dark mode and visually blue in light
mode — directly contradicting the developer comment at lines 39-40
(`"All blue-* utilities ... automatically become purple/violet"`)
which described the intent perfectly but was only half-implemented.

## Fix

Per the ticket's "fix at the root via the existing CSS-variable-swap
strategy" guidance, the entire fix lives in `apps/web/src/index.css`.
No component files were edited.

1. Added a new `:root` block with the brand purple shades for
   `--color-blue-50` through `--color-blue-950`. Same hue (287°) as
   dark mode for brand coherence; lightness/chroma are tuned to be
   more saturated than the dark-mode shades, since light-mode UI sits
   on white surfaces and needs higher contrast purples to read as the
   accent color.

2. Kept the existing `.dark` overrides of those same variables. Cascade
   order means light mode picks up the `:root` shades and dark mode
   picks up the `.dark` overrides — so dark mode is unchanged.

3. Added a `.prose { --tw-prose-links: oklch(46% 0.22 287); }` block
   so rendered markdown links in light mode pick up the brand purple.
   The Tailwind Typography default for `--tw-prose-links` is a slate
   value, so the `--color-blue-*` swap alone does not reach it.

4. Did NOT touch the existing `.dark .text-blue-{600,700,800}` per-
   element overrides at lines 140-142. They tweak text lightness (75-
   82%) on top of the variable swap so that accent text reads on dark
   surfaces. Removing them would dim that text in dark mode, which
   would regress dark-mode legibility unrelated to this ticket.

5. Did NOT regress any of #333's `.dark .bg-slate-*` /
   `.dark .bg-gray/neutral/zinc-*` overrides — those rules at lines
   118-137 are unchanged, and the dark-mode primary-button surface
   contract still holds.

## Light-mode purple values (chosen)

```css
:root {
  --color-blue-50:  oklch(97% 0.018 287);
  --color-blue-100: oklch(94% 0.04 287);
  --color-blue-200: oklch(88% 0.07 287);
  --color-blue-300: oklch(80% 0.12 287);
  --color-blue-400: oklch(70% 0.18 287);
  --color-blue-500: oklch(60% 0.22 287);
  --color-blue-600: oklch(53% 0.23 287);   /* primary */
  --color-blue-700: oklch(46% 0.22 287);
  --color-blue-800: oklch(38% 0.19 287);
  --color-blue-900: oklch(30% 0.15 288);
  --color-blue-950: oklch(20% 0.10 290);
}
```

The `-600` shade is approximately Tailwind's `violet-600`
(`oklch(0.541 0.281 293.009)`) nudged to hue 287° to match the
dark-mode purple. Channel-level: `bg-blue-600` resolves to roughly
`rgb(108, 44, 217)` in sRGB, which is a clearly violet primary.

## WCAG AA contrast (verified)

- `bg-blue-600` (≈ `rgb(108, 44, 217)`) + `text-white`: contrast
  ratio ≈ 5.6:1 → passes AA (≥ 4.5:1).
- `text-blue-600` on `bg-white` (`#ffffff`): same 5.6:1 → passes AA.
- `text-blue-700` on `bg-white`: ≈ 7.4:1 → passes AAA.
- `text-blue-700` on `bg-slate-50` (light slate): ≥ 7.0:1 → passes AAA.

The Playwright test asserts the `≥ 4.5:1` constraint at runtime
against the actual computed `background-color` so any future drift
in the OKLCH values is caught.

## Test added

`e2e/light-mode-purple.spec.ts` — Playwright spec that:

1. Mocks the GitHub synced-repos endpoint so `/repositories` enters
   the "with repos" branch and the `data-testid="manage-repos-button"`
   (a `bg-blue-600 text-white` button) renders.
2. Forces light mode via `emulateMedia({ colorScheme: 'light' })`,
   sets `localStorage.theme = 'light'`, removes the `.dark` class,
   and reloads — then asserts `html` does NOT have the `dark` class.
3. Reads the computed `background-color` of the button.
4. Asserts:
   - **r > g** (true for any purple/violet, false for default
     Tailwind blue-600 which is `rgb(37, 99, 235)`). This single
     channel inequality is the simplest unambiguous "this is purple,
     not blue" guard.
   - **Distance from rgb(37, 99, 235) > 30** as a belt-and-suspenders
     check that the result is not silently regressing back to
     Tailwind's default blue-600.
   - **WCAG contrast ≥ 4.5:1** against white text computed via the
     standard relative-luminance formula.

The test runs in real Chromium (not jsdom) so OKLCH and CSS variable
cascade are fully resolved.

## Audit: "true blue" usages flagged (no edits made)

Per ticket guardrails, the fix lives entirely in `index.css` and no
component file was modified. However, the ticket asked for an audit
of places where `blue-*` is deliberately used to mean ACTUAL blue
(GitHub brand badge, "info" indicator, etc.) and would be incorrectly
swept up by the purple remap.

A grep for `blue-` under `apps/web/src/` returned 57 files. None of
them appear to be using `blue-*` to mean "literal blue" semantically
in the issue's sense:

- **GitHub brand surfaces** (e.g. `GitHubReconnectBanner`,
  `Repositories`, `Settings`, `RepoPickerModal`, `ScanRepositoryModal`)
  do NOT use `blue-*` for the GitHub brand. GitHub branding in this
  app is rendered via the Octocat svg / dark slate buttons, not via
  blue background classes. Confirmed `GitHubReconnectBanner.tsx` has
  zero `blue-` references.
- **"Info" indicators** appear on `VoicePage`, `Settings`,
  `DocumentEditor`, `TemplatePicker`, `Sidebar`, `FileTree`,
  `AIAdvisor`, but the spot checks confirm they are the standard
  brand-accent treatment (links, focus rings, primary actions),
  intended to be purple in both modes. None were a "this should be
  literal blue because it means information" case.

If a future component wants ACTUAL Tailwind blue (e.g. a third-party
brand badge that must remain blue for legal reasons), the recommended
escape hatch is to use `sky-*` / `cyan-*` (not remapped) or a literal
hex via `style={{ backgroundColor: '#...' }}` / `bg-[#...]`. This is
documented for posterity; no immediate code change is needed.
