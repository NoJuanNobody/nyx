# Ticket #197 — Sprint Gatekeeper Integration

## What was done

1. Created `apps/api/src/services/gatekeeper.service.ts` with `evaluateGate()` that enforces:
   - Content must not be empty
   - Content must meet minimum length (100 characters)
   - Valid stage transition order (sequential, no skipping, no backward moves)
   - Supports custom stage orderings (for lifecycle-specific pipelines)
   - Returns `{ passed, checks }` with detailed per-check results

2. Integrated gatekeeper into `PUT /api/documents/:id` in `apps/api/src/routes/documents.ts`:
   - When `body.stage` is provided, fetches current document and evaluates the gate
   - If gate fails, returns 422 with the list of unmet conditions
   - Uses effective content (body.content if provided, otherwise existing doc content)

3. Added 16 unit tests in `apps/api/src/services/__tests__/gatekeeper.service.test.ts` covering:
   - Happy path sequential transitions
   - Empty/whitespace content rejection
   - Below-minimum-length content rejection
   - Backward transition rejection
   - Stage skipping rejection
   - Same-stage rejection
   - Unrecognized target stage rejection
   - Null current stage (must start at first stage)
   - Custom stage ordering support
   - Unknown current stage passthrough
   - Multiple simultaneous failures

## Notes
- The default stage order matches the `documentStageEnum`: conception → definition → architecture → implementation → execution
- The `evaluateGate` function accepts an optional `stageOrder` parameter for lifecycle-specific pipelines
- Pre-existing test timeouts in `feedback.service.test.ts` and `context-matching.service.test.ts` are unrelated
