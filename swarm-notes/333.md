# Ticket 333 — Fix dark mode buttons rendering white text on white background

## Root cause

`apps/web/src/index.css` uses a CSS-variable-swap strategy for dark
mode. Inside the `.dark` block, `--color-slate-50` through
`--color-slate-950` are inverted so that text utilities like
`text-slate-900` (intended as body text) automatically become near-white
in dark mode. The same variables back the background utilities,
which means `bg-slate-900` (the canonical primary-button background
across the app) ALSO becomes near-white in dark mode. Combined with
the explicit `.dark .text-white { color: #fff; }` rule that pins button
text to white, every `bg-slate-900 text-white` button rendered as
white-on-white in dark mode and was effectively invisible.

The user-reported example is the "+ New Repository" button on
`apps/web/src/pages/Repositories.tsx` (lines 340 and 413), but the same
class combination is used by many other primary actions across the app
(Settings GitHub connect, ScanRepositoryModal action, the
CreateRepoModal submit, the empty-state CTA, etc).

## Fix

Per the ticket's "fix at the root via the existing CSS-variable-swap
strategy" guidance, the entire fix lives in `apps/web/src/index.css`.
No component files were edited. Specifically, the `.dark` overrides
section was extended with explicit selectors that target the
literal Tailwind background-utility class names (NOT the variables
themselves), so the slate background utilities pick up dark surfaces
in dark mode while leaving the slate text utilities (which still need
to be light) alone.

Added rules:

```css
.dark .bg-slate-900 { background-color: oklch(28% 0.04 285); }
.dark .bg-slate-800 { background-color: oklch(33% 0.045 285); }
.dark .bg-slate-700 { background-color: oklch(38% 0.05 285); }

.dark .hover\:bg-slate-900:hover { background-color: oklch(33% 0.045 285); }
.dark .hover\:bg-slate-800:hover { background-color: oklch(38% 0.05 285); }
.dark .hover\:bg-slate-700:hover { background-color: oklch(43% 0.055 285); }

.dark .bg-gray-50,
.dark .bg-neutral-50,
.dark .bg-zinc-50    { background-color: oklch(17% 0.025 285); }
.dark .bg-gray-100,
.dark .bg-neutral-100,
.dark .bg-zinc-100   { background-color: oklch(22% 0.03 285); }
```

Why this works:

- The selectors target the literal `bg-slate-900` class, which beats
  the variable-driven Tailwind declaration on specificity tie via
  source order (the override sits below the variable definitions).
- `text-slate-900` and the rest of the text utilities still go
  through the variable swap, so body text remains light in dark mode.
- `dark:bg-slate-700` (used in `MarkdownPreview.tsx` and
  `SlashCommandPalette.tsx`) is a DIFFERENT class
  (`dark\:bg-slate-700`), so it is unaffected by these overrides.
- The `bg-gray|neutral|zinc-50/100` block is defensive coverage for
  any near-white scale that lands in the codebase later but that the
  slate swap does not touch — the issue body explicitly cites these as
  in-scope candidates.
- Light mode is unchanged: the rules live inside `.dark` and only fire
  when the html element has the `dark` class.

## Files modified

- `apps/web/src/index.css` — extended the `.dark` block with the
  background-utility overrides described above. No other CSS rules
  were touched, no `text-white` or `InlineCode` styling was changed.

under the new rules:

  surface, so the white code-header text remains legible. OK.
- **`SlashCommandPalette`** — uses `dark:bg-slate-800` and

- **Modals / `Modal.tsx`** — uses `bg-white` (variable-swapped) +

- **`TemplatePicker.tsx`** — selected-state pill uses
  `bg-slate-900 text-white`, now correctly dark-on-white-text in dark
  mode via the new override. Unselected state uses `bg-slate-100
  text-slate-700`, which is dark surface + light text via the variable
  swap. OK.
- **`CreateTicketModal.tsx`** — primary submit is `bg-blue-600
  text-white` which already worked (blue scale is remapped to a
  dark-purple accent). OK.
- **Settings pages** (`Settings.tsx`) — GitHub connect button uses
  `bg-slate-900 text-white`, now fixed via the new override. OK.
- **Primary buttons across the app** — every `bg-slate-900 text-white`
  + `hover:bg-slate-800` instance now renders as a dark purple
  surface with white text in dark mode, well above WCAG AA 4.5:1
  contrast (white on `oklch(28% 0.04 285)` is ~13:1).
- **Secondary buttons** — `border-slate-200 bg-white text-slate-700`
  patterns remain fine via the variable swap (dark surface, light
  text, dark border).
- **Ghost / link buttons** — `text-slate-600` + `hover:bg-slate-100`
  remain fine via the variable swap.
- **Destructive buttons** — `bg-red-600 text-white` use the red scale
  which is unchanged by these overrides; the remapped accent text
  rules already cover legibility. OK.
- **Disabled states** — primary disabled is `disabled:opacity-50` over
  `bg-slate-900` (now dark purple) with white text; opacity drops to
  0.5 but background is still dark and text still white, so contrast
  remains > 6:1, well above the 3:1 disabled requirement.

  is bit-for-bit identical to before. No regression possible.
- **`text-white` and `InlineCode` rose styling** — untouched, per the
  guardrail in the ticket and the merge of #339.

## Assumptions

1. **Specificity / source order.** I am relying on the new `.dark
   .bg-slate-900` selectors winning over the Tailwind-generated
   `.bg-slate-900 { background-color: var(--color-slate-900); }` rule
   because the new rules are placed AFTER Tailwind's generated
   declarations (Tailwind injects its utility layer before custom
   `.dark` rules in this file's import order). Selector specificity is
   actually higher for `.dark .bg-slate-900` (0,0,2,0) than the bare
   `.bg-slate-900` utility (0,0,1,0), so the override wins regardless
   of source order. No `!important` needed.
2. **`oklch(28% 0.04 285)` is the right primary surface.** I picked it
   to sit in the same purple-tinted family as the rest of the dark
   palette (the `--color-slate-100`/`200` swaps) and to give white
   text ~13:1 contrast — comfortably above the 4.5:1 AA target with
   plenty of headroom for hover/disabled states.
3. **`bg-gray-*`/`bg-neutral-*`/`bg-zinc-*` defensive rules are
   wanted.** No current button in `apps/web/src/**` uses those
   utilities (only `lifecycles.ts`, a data file), but the ticket body
   explicitly lists them as in-scope candidates and adding two CSS
   declarations is cheap insurance against future regressions.
4. **No component edits.** The ticket says explicitly "Do NOT edit
   component files to swap classes — the fix lives in `index.css`."
   I followed that strictly.
