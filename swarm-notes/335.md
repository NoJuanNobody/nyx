# 335 — Allow reorganizing nested folders via drag-and-drop

## What changed

**apps/web/src/components/FileTree.tsx**
- Extracted the descendant-path rewrite logic that previously lived inline in `handleFolderRenameSubmit` into a top-level, exported pure helper `rewriteDescendantPaths(items, oldPrefix, newPrefix)`. Both `handleFolderRenameSubmit` and the new drop-folder path now call the same helper via a shared `applyFolderMove` callback, so rename and move share one tested implementation.
- Added two more exported pure helpers used by the drop logic and unit tests:
  - `wouldCreateCycle(sourcePath, targetParentPath)` — guards against drop-on-self and drop-into-descendant. Importantly it tests `targetParentPath.startsWith(sourcePath + '/')` so look-alike names like `/A` vs `/Apple` don't false-positive.
  - `computeMovedFolderPath(sourcePath, targetParentPath)` — peels the leaf segment off the source and re-parents it under the target (handles `'/'` root special case).
- Added two MIME constants: `DRAG_MIME_DOC = 'application/nyx-doc-id'` and the new `DRAG_MIME_FOLDER = 'application/nyx-folder-path'`.
- The folder row container is now `draggable={!isRenaming}`. `onDragStart` writes the folder path to `dataTransfer` under `application/nyx-folder-path`, sets `effectAllowed='move'`, and stashes the source path in a module-scoped `activeFolderDragSource` variable. `onDragEnd` clears it.
- `Folder.handleDragOver` now recognizes both MIME types. For folder drags, it consults `activeFolderDragSource` and, if `wouldCreateCycle(source, node.path)` is true, sets `dropEffect='none'` and skips the highlight, so neither drop-on-self nor drop-into-descendant shows the blue ring. The module-level source tracker is necessary because the HTML5 DnD spec only exposes payload **types** during dragover, never **values**.
- `Folder.handleDrop` reads either MIME and dispatches to `onDropDoc` (existing) or the new `onDropFolder` callback.
- New `applyFolderMove(oldPath, newPath)` `useCallback` inside `FileTree`: rewrites `folders` via `rewriteDescendantPaths`, persists via `saveFolders`, rewrites `expandedFolders` the same way (so anything expanded under the old path stays expanded under the new path — mirrors the rename flow), then iterates `documents` and persists every descendant doc's new path via `updateDocument` (the same direct API call the rename flow uses), then invalidates the documents query.
- New `handleDropFolder(sourcePath, targetParentPath)` `useCallback`: short-circuits on cycle/self via `wouldCreateCycle`, computes the new path via `computeMovedFolderPath`, and (after a final `newPath === sourcePath` no-op check) calls `applyFolderMove`.
- The root drop zone (the scrollable file-tree container) `onDragOver` and `onDrop` now also recognize `application/nyx-folder-path` and route to `handleDropFolder(sourcePath, '/')`.
- The folder context menu (`buildFolderMenuItems`) gained a "Move to…" submenu listing every valid destination folder (excluding the source itself, every descendant, and the source's current parent — the latter so the menu doesn't list a no-op move). When the source isn't already at root, the submenu also includes a "/  (root)" option. The submenu items call `handleDropFolder` directly, so the keyboard fallback uses the exact same code path as drag-and-drop.

**apps/web/src/__tests__/components/FileTreeFolderMove.test.tsx (new)**
- 17 tests across four describe blocks, all passing.
- `rewriteDescendantPaths`: 5 tests covering exact match, nested descendants, look-alike-name false positives (`/Apple` vs `/A`), moves to root, and unchanged inputs.
- `wouldCreateCycle`: 5 tests covering self, direct descendant, deep descendant, sibling moves, root moves, and the `/Apple` look-alike case.
- `computeMovedFolderPath`: 3 tests for sibling-parent, root, and root-source moves.
- `FileTree folder drag-and-drop` integration block (4 tests): mounts `FileTree` with a mocked `lib/api`, seeds folders via `localStorage`, and asserts:
  - dragging `/A/Child` onto `/B` calls `updateDocument('doc-1', { path: '/B/Child' })` and persists `/B/Child` (and removes `/A/Child`) in `nyx:folders`.
  - dragging `/A` onto `/A/Child` (cycle) is fully no-op: zero `updateDocument` calls and folder list unchanged.
  - dragging `/A` onto itself is a no-op.
  - the folder context menu surfaces a "Move to…" entry.

**e2e/file-tree.spec.ts**
- Added test `26.7 — drag a nested folder onto a sibling moves it`. Pre-seeds `/A`, `/A/Child`, `/B` via `localStorage` + reload, expands A, then dispatches synthetic `dragstart`/`dragover`/`drop` events with a real `DataTransfer` carrying `application/nyx-folder-path = '/A/Child'`. Asserts `Child` now appears under `B`, reloads, and confirms `/B/Child` persists in `nyx:folders` (and `/A/Child` does not).

## Assumptions / design notes

- **Module-scoped drag source tracker.** The HTML5 DnD spec only exposes `dataTransfer.types` during dragover — payload values are read-protected outside of `drop`. To support live cycle/self detection in the highlight (which the AC requires: "Dropping a folder onto one of its own descendants is prevented — the drop is rejected, dropEffect is set to 'none', and the UI does not show a drop highlight"), I used a module-level `activeFolderDragSource` set on `dragstart` and cleared on `dragend`/`drop`. This is a small concession to the API but is contained inside `FileTree.tsx` and only ever holds an in-flight string, so it shouldn't cause cross-test pollution (the tests clear it as a side effect of dispatching real events).
- **Folder data model.** Per the issue, folders live only in client-side state (`folders` array in `localStorage`) plus the derived doc paths. So "move folder" really is "rewrite the folders list + bulk-update descendant doc `path` fields." No new API endpoint was introduced. The doc updates are fired sequentially via direct `updateDocument` calls (matching what `handleFolderRenameSubmit` already does); the issue explicitly calls out a perf/batch endpoint as a follow-up.
- **`expandedFolders` preservation.** Mirrored the rename flow but used the new `rewriteDescendantPaths` helper on a temporary array, then re-built the Set. This collapses the inline loop into the same shared helper.
- **"Move to…" submenu scope.** I excluded the source's current parent so the menu never offers a no-op move. I considered also building a tree-style picker dialog instead, but the existing `ContextMenu` already supports nested submenus and keyboard navigation, so a flat list of valid target paths felt consistent with the rest of the file tree's UX and avoided introducing a new modal component for a fallback affordance.
- **No e2e for "Move to…" menu path.** The unit-test layer covers both the menu surface area (item is present) and the underlying `handleDropFolder` logic (cycles, no-op, success). The Playwright spec covers the actual drag-and-drop flow end-to-end including persistence across reload, which is what the AC explicitly required. I did not add a separate e2e for the menu fallback to keep the test count lean.

## Governance conflicts

NONE. The change touches only `FileTree.tsx` and its test surface, introduces no new external dependencies, no AI-provider coupling, no env vars, no secrets, and no new API endpoints. It strictly matches the AC enumerated in issue #335.

## Follow-up items

- **Batch the descendant-doc updates.** Today `applyFolderMove` fires one `updateDocument` PATCH per descendant doc, the same way rename does. The issue called this out as fine for now and suggested a follow-up batch endpoint for perf. If folder moves of large subtrees become a hot path, opening a `PATCH /api/documents/bulk-path` endpoint would let both rename and move share a single request.
- **`activeFolderDragSource` could move into a React context** if more drag-aware components ever need to read it. For now, scoping it to `FileTree.tsx` is fine — folders only live there.
- **Bundle-size warning** in `pnpm build` (`dist/assets/index-*.js` 1.27 MB) is pre-existing and unrelated to this change.
