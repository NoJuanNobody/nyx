# 342 — Set a stage on documents created by the repo scan flow

## What changed

**apps/api/src/routes/onboarding.ts**
- Added a top-of-file constant `SCAN_DEFAULT_STAGE = 'implementation'` with a JSDoc explaining why `implementation` is the natural default for repo-scan docs (the docs are AI-generated reverse engineering of code that already exists).
- Added `stage: SCAN_DEFAULT_STAGE` to the per-module `db.insert(documents).values({...})` call in the `for` loop that persists `result.moduleDocs`.
- Added `stage: SCAN_DEFAULT_STAGE` to the merged-overview `db.insert(documents).values({...})` call.
- The literal `'implementation'` is referenced exactly once in the file (inside the constant); both insert sites read the constant.

**apps/api/src/__tests__/routes/onboarding.test.ts**
- Updated the `mockDbInsertReturning` test helper to:
  - Optionally accept a `capturedValues` array and push every payload that is passed to `.values(...)` into it, so tests can assert on the inserted columns.
  - Include `stage: 'implementation'` in the mocked returned row, matching what a real Drizzle insert would now return.
- Added a new integration test: `POST /api/onboarding/scan persists every document with stage 'implementation'`.
  - Mocks `onboardingService.scanRepository` to return 3 module docs (`Auth`, `API`, `Web`) plus a merged overview, against `acme/widgets`.
  - Captures every `.values(...)` payload that the route passes to `db.insert(documents)`.
  - Asserts that `body.documents` has length 4 (3 modules + 1 overview).
  - Asserts that **every** captured insert payload has `stage === 'implementation'`.
  - Additionally asserts the per-module inserts (`Auth`, `API`, `Web`) and the overview insert each individually carry `stage === 'implementation'`, so a future regression that only sets stage on one of the two insert sites would still fail this test.
- Did **not** need to update any other existing onboarding test that expected `stage` to be `null` — none of them asserted on stage, they only asserted on `body.documents.length`, `body.moduleCount`, and `body.fileCount`. Those still pass unchanged.

- `apps/api/src/services/onboarding.service.ts` — **unchanged.** The service still returns pure data (`{ files, suggestedDocs, moduleDocs, moduleCount, fileCount }`). The default stage lives at the route layer because only the route writes to the DB. No `stage` was plumbed through `scanRepository`.
- `POST /api/onboarding/scan` request body — **unchanged.** Still `{ owner, repo, teamId }`. No `stage` parameter was added; that would be a separate, larger feature (onboarding stage picker) per the issue's notes.
- No backfill of existing `stage = null` rows. The fix only affects documents created from the moment it ships, per the acceptance criteria. No migration was added.
- No per-module heuristics. Both per-module docs and the overview doc default to the same `implementation` stage, per the issue's "Do not attempt to set stages per-module based on heuristics" guidance.
- No UI changes in the onboarding wizard.

## Follow-up items

- **Backfill of historical `stage = null` documents from prior scans**: explicitly out of scope per the issue's acceptance criteria ("Existing documents in the database with `stage = null` are **not** backfilled by this change"). If desired, a separate ticket should add a one-time migration that sets `stage = 'implementation'` on rows in `documents` whose `path` matches `/repos/%` and whose `stage IS NULL`.
- **Onboarding stage picker UI**: the issue notes call out that adding a `stage` parameter to the `/scan` request body would be a separate, larger feature. If the team later wants users to pick a stage at scan time (e.g., for greenfield repos where `architecture` would be more appropriate), open a new ticket.
- **`overview` doc as `architecture` instead of `implementation`**: the issue notes mention this as an option ("If you feel the overview doc is more architectural than implementation-y..."). I chose to keep both per-module and overview at `implementation` for consistency, simplicity, and because the merged overview is generated from the same per-module AI output, which is itself derived from real source files. If product wants the overview to land on `architecture`, that's a one-line change (a second constant) and an updated test assertion.
