# #348 — Speed up repo indexing: tarball fetch, Haiku, parallel phases

Branch: `swarm/348`
Base: `main` @ `00991aa`

## What shipped

Six bundled perf improvements to `onboardingService.scanRepository` that
should bring a typical 80-file / 7-module scan from ~2 minutes down to
~30 seconds. The public shape of `POST /api/onboarding/scan` is
unchanged (response body, error codes, status semantics).

### 1. Tarball fetch (Change 1)

- New helper `fetchRepoTarball(accessToken, owner, repo, ref = 'HEAD')`
  in `apps/api/src/services/onboarding.service.ts`. Single
  `GET /repos/{owner}/{repo}/tarball/{ref}` replaces up to 80 Contents
  API calls.
- Response body (`ReadableStream`) is bridged to a Node stream with
  `Readable.fromWeb`, piped through `zlib.createGunzip()` and then
  through `tar-stream`'s `extract()`. Backpressure handled via
  `stream/promises.pipeline`.
- The existing `shouldSkip` + `isSourceFile` + `MAX_FILE_SIZE` filters
  are applied **during extraction** (both via the tar header `size` and
  a running byte counter inside the data handler) so nothing above
  100KB is ever buffered. Memory stays bounded.
- Tarball path prefix `{repo}-{shortSha}/` is stripped so map keys are
  repo-relative and match what `groupFilesIntoModules` expects.
- `fetchFilesParallel` and `fetchFileContent` were deleted. There is
  now one code path: tarball → in-memory Map → module sampling.
- `scanSmallRepo` also uses the tarball map — no forked code.
- On tarball failure we throw a structured `"GitHub tarball fetch failed: <status> <text>"` /
  `"GitHub tarball stream failed: <reason>"` error. **No fallback to per-file Contents API**.
- New dep: `tar-stream` + `@types/tar-stream` (standard pure-JS Node tarball streamer).

### 2. Haiku for per-module docs (Change 2)

- `ai.service.ts` → `bootstrapModuleDocs` now uses `MODEL_FAST` (Haiku).
- `mergeModuleDocs` intentionally stays on `MODEL` (Sonnet) for
  synthesis quality. Comment added so a future agent doesn't "fix" it.
- `max_tokens` stays at 2048.
- New unit tests in `ai.service.test.ts` (`onboarding scan model split`)
  assert the model on each function so regressions are caught:
  - `bootstrapModuleDocs` → matches `/haiku/i`, does NOT match `/sonnet/i`
  - `mergeModuleDocs` → matches `/sonnet/i`, does NOT match `/haiku/i`

### 3. Phase 4 parallelism (Change 3)

- Since Change 1 gives us everything in memory, the outer
  `for (const [mod, paths] of sampled)` network loop is gone. Replaced
  with a pure in-memory pass that looks each sampled path up in the
  tarball Map.

### 4. AI concurrency raised 3 → 6 (Change 4)

- `AI_CONCURRENCY = 6` with a comment noting the Anthropic rate-limit
  rationale and warning future agents not to raise it further without
  checking current limits.
- The bounded batching loop (`for i += AI_CONCURRENCY` + `Promise.all`
  per batch) is preserved — we do **not** call `Promise.all` over all
  modules at once.
- New unit test: `AI concurrency bound > never has more than AI_CONCURRENCY module AI calls in flight at once`.
  Runs 12 modules through the batching pattern, tracks max in-flight
  via counter, asserts ≤ `AI_CONCURRENCY` and that `AI_CONCURRENCY === 6`.

### 5. Scan result cache (Change 5)

- Module-level `Map<string, { result: ScanResult; expiresAt: number }>`
  in `onboarding.service.ts`, key `${owner}/${repo}@${headSha}`.
- `SCAN_CACHE_TTL_MS = 10 * 60 * 1000` at the top of the file.
- HEAD SHA is captured from `GET /git/trees/HEAD?recursive=1`
  (`data.sha`) — no extra commits-endpoint round trip.
- On cache hit, `scanRepository` returns the cached result with **zero
  tarball calls and zero AI calls**. (One tiny tree-fetch call still
  happens to get the SHA — see "Scoped interpretation" below.)
- On cache miss, the full pipeline runs and the result is written to
  the cache before returning.
- `invalidateScanCache(owner, repo)` is exported for manual busting
  (not used by the route today — future feature).
- `_resetScanCache()` exported for test hygiene.
- Unit tests:
  - `returns the cached result on a repeat scan of the same commit` —
    asserts second call does NOT invoke tarball fetch and does NOT
    invoke any AI methods.
  - `re-runs the full pipeline when HEAD SHA changes` — asserts
    `mergeModuleDocs` is called twice across two different SHAs.
  - `invalidateScanCache drops entries for the given {owner, repo}` —
    asserts cache busting forces a re-run.
- Scoped interpretation: the ticket body says "no further GitHub or AI
  calls" on cache hit; my task doc says "zero GitHub calls". Since the
  cache key requires a HEAD SHA, strictly zero GitHub calls is
  impossible without holding server-wide SHA state. I implemented the
  ticket-body-intent version: one small tree-fetch (cheap, single
  call), then cache hit → skip tarball + all AI. The cache is
  protecting against the expensive stuff (tarball + 7+ AI calls), not
  against a <0.5s tree fetch.
- **In-memory only** — no Redis, no Postgres.

### 6. Bulk DB insert (Change 6)

- `routes/onboarding.ts` now builds `moduleRows` + `overviewRow` and
  performs a single
  `db.insert(documents).values([...moduleRows, overviewRow]).returning()`.
- **Every row preserves `stage: SCAN_DEFAULT_STAGE`** — #342's stage
  default fix is not regressed.
- Response `savedDocs` preserves the same `{ id, title, path }` shape
  and ordering (module docs first, overview last).
- Tests updated:
  - `mockBulkInsert` helper captures the array passed to `.values(...)`
    and resolves to a derived doc list so order-preservation can be
    asserted.
  - New assertion: `expect(mockDb.insert).toHaveBeenCalledTimes(1)` on
    the multi-doc case.
  - New assertion: inserted titles match the expected order
    `['Services', 'Components', 'myorg/myrepo Overview']`.
  - Stage assertion loop unchanged — every captured row still has
    `stage === 'implementation'`.
