# Tickets, posting and Sprint Gatekeeper (`nyx-core::tickets`)

Ticket AI-69. Rust port of ticket creation / posting, bulk review, the tickets board, sprint
capacity, the Sprint Gatekeeper and the non-agent half of orchestration. No agent, chat, Stripe or
Clerk code.

## Flow

```
Advisor (LLM) -> TicketGenerator -> DraftStore::create_batch (dedupe vs tickets + live drafts)
   draft --edit/set_destination--> draft --approve--> approved --post--> posting --> posted
                                                                            \--> failed --retry--> approved
   draft|approved|failed --dismiss--> dismissed
posted -> tickets row (board) + audit_trail ticket_created + timeline ticket_created
```

### Posting guarantees (`review::post`)

- **Claim before call**: `approved|failed -> posting` is one conditional UPDATE; a concurrent post
  gets `Error::Conflict` and never reaches the tracker.
- **Idempotent**: posting a `posted` draft returns the recorded external ref; the tracker is not
  called. A crash between "posted" and the board-row link is healed on replay (the ticket is
  matched by document + provider + URL, never duplicated).
- **Lost responses**: a transport error / 5xx / unparseable 2xx marks the draft
  `failed` + `outcome_unknown`. The next attempt calls `TicketTracker::find_by_title` first and
  *adopts* an existing issue instead of creating a second one. `recover_interrupted` turns drafts
  stranded in `posting` (crash) into that same state; the wiring layer should call it at startup.
- **Unique indexes** back it up: one live draft per normalised title per document; one draft per
  `(destination_key, external_id)`.
- **Batch**: `post_batch` is sequential, continues past per-draft failures, and halts (leaving the
  rest `approved`) on a rate limit or auth failure. The TS 500 ms pacing between calls is the
  caller's job.
- **Traceability**: every posted body ends with `Generated by Nyx from "<title>"
  (nyx://document/<id>)` plus a `nyx-ref:doc=<id>;draft=<id>` line, so the issue links back to the
  document and the document links to the issue (`tickets` row, `Ticket.external_url`).

## Parity gaps and deliberate changes (honest list)

- **Linear tickets reach the board** (migration 180, `0180_tickets_linear.sql`). SQLite cannot widen a
  CHECK, so `tickets` is rebuilt (rows stashed, table dropped and recreated under the same name so the
  `REFERENCES tickets(id)` of `audit_trail` / `ticket_drafts` stay valid, `defer_foreign_keys` until
  COMMIT) and existing posted Linear drafts get a `linear` ticket row (status `open`, corrected by the
  next status sync) and are linked. `TicketProvider::Linear` exists; `TrackerKind::ticket_provider()`
  returns a plain `TicketProvider` (it was an `Option`); `TrackerSink` and `review::post` create board
  rows for Linear. Board derivations: repo name = workspace slug from
  `linear.app/<workspace>/issue/...`; the rebuilt `Destination::Linear.team_id` is the team *key* (`ENG`
  of `ENG-42`), which is enough for status sync (the Linear tracker ignores the destination there).
- **Jira/Linear over the live transport are untested against real services.** Request building and response parsing plus an
  `HttpTransport`-backed adapter; `nyx-net` supplies the transport (same as `git_provider`).
  The Jira/Linear request shapes follow the public docs and fixtures; they have **not** been run
  against live services. Jira search uses `/rest/api/3/search/jql` (the TS used the older
  `/rest/api/3/search`, which Atlassian is retiring). The full Jira/Confluence/Slack clients are AI-71.
- **Jira labels are off by default** (`JiraTracker::with_labels(true)` to send them): the field must
  be on the project's create screen or Jira answers 400. Linear labels are folded into the
  description (Linear wants label ids).
- **Jira description is ADF** (headings, lists, code blocks, bold/code/link marks). TS sent the
  whole markdown as one text node.
- **GitHub Projects v2 sprint source is not ported.** It is GraphQL outside `GitProvider`;
  `SprintSource` is the seam (`JiraSprintSource`, `LinearSprintSource` (active cycle), and
  `StaticSprintSource` exist). `defer`'s "move to Backlog column" is `SprintSource::move_to_backlog`.
  The deferred set is in memory like TS but serialisable (`SprintBoard`) so it can be persisted.
- **Status sync** derives the destination from the ticket URL (TS used the team's *first*
  configured repo, wrong for tickets in other repos). Git hosts have no single-issue read in
  `GitProvider`, so `fetch_status` lists issues (all pages, capped by the provider) and finds the
  id. Jira maps by status name (TS rules) then by status category; sync without a configured
  tracker leaves the ticket unchanged and is not counted by `sync_all`.
- **`update_status_by_external_id`** returns every match (TS returned the first) and accepts a URL
  prefix, because issue numbers repeat across repos.
- **Capacity maths**: `round(used/total*100)` half-up, threshold applied to the rounded percent
  (159/200 = 79.5% -> 80 -> over). Zero total capacity is guarded (TS gave NaN).
- **Gatekeeper readiness (`assess_readiness`) is new**; the TS only had the stage gate and the
  capacity banner. Rules: `sprint.not_empty`, `sprint.capacity_warning` (>=80%),
  `sprint.capacity_blocker` (>=100%), `ticket.{title,body_length,acceptance_criteria,spec_linked,
  not_oversized,unique_title}`, `spec.{min_content,stage_reached,unresolved_markers,quality,
  quality_good}`. Score = weighted share of rules passed (blocker 3, warning 1). Thresholds are in
  `ReadinessConfig`. Note `lifecycle::transition` documents that the strict sequential gate was
  dropped for manual stage changes (#197); `evaluate_stage_gate` is kept as the explicit opt-in.
- **Orchestration**: `dependsOn` entries that match a step *name* in the same pipeline are resolved
  to ids (TS stored them verbatim, so in-pipeline dependencies could not be expressed); raw ids
  still work and dangling ids never unblock, as in TS. State is in memory, as in TS.
- **Not ported**: `claudeInsightsService` GitHub half (AI-75 doc), folder-level suggestions
  (`generateFolderSuggestions`: compose `TicketGenerator::from_document` over a folder's documents
  in the caller), async job wrappers (`jobService`), notifications and onboarding side effects of
  the route (use `notify`), GitLab/Bitbucket token-expiry error class (mapped to
  `TrackerError::Auth`).
- `ticket_suggestions` (AI-75, `pending/approved/dismissed`) is untouched; `ticket_drafts` is the
  posting-aware replacement. No data bridge between them yet.

## Wiring notes (AI-74)

- Build a `TrackerSet` from stored integrations: `GitProviderTracker::new(Arc<dyn GitProvider>)` per
  git host, `JiraTracker::new(JiraCredentials, transport)`, `LinearTracker::new(key, transport)`.
- Generation: `TicketGenerator::new(Advisor::new(&llm, &models)).from_document(..)` ->
  `DraftStore::create_batch(doc, user, drafts, destination)`.
- `Destination::from_identifier(provider, "owner/repo" | "PROJ" | team_id)` mirrors the TS wire shape.
- Credit metering of LLM calls goes through `ai::UsageSink` as documented in `ai.md`.
